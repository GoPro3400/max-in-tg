# Участие В Разработке

Личный проект одного человека, self-hosted мост между веб-сессией MAX и Telegram. PR
приветствуются. Исходный код хранится в Git; секреты и runtime-состояние в Git не
попадают.

---

| Путь | Описание |
|------|----------|

## Что НЕ Коммитить

| Путь | Причина |
|------|---------|
| `.env` | Содержит секреты |
| `data/` | Runtime данные и Chrome profile |

Все эти пути уже закрыты в `.gitignore`.

## Рабочий Процесс

### Ветки

```bash
fix/<short-change-name>
feat/<short-change-name>
```

### Правила

1. Форк → ветка → pull request в `main`
2. Делать изменения небольшими и понятными для ревью
3. Перед коммитом — синтаксические проверки и `npx vitest run`
4. Обновлять документацию при изменении переменных, деплоя или UX
5. Обновлять `CHANGELOG.md` (раздел `[Unreleased]`)

`.github/workflows/ci.yml` прогоняет `npm test` и проверяет compose-файлы на каждом PR —
запусти `npx vitest run` локально перед отправкой. Если PR меняет `Dockerfile`,
`.dockerignore`, зависимости или скрипты запуска и проверки образа,
`.github/workflows/image.yml` ещё и собирает образ (для amd64 и arm64) и проверяет его
через `scripts/smoke-image.sh` (в него входят настоящие конвертации медиа —
`scripts/smoke-media.mjs`).

### Как выходит релиз

Версии — `MAJOR.MINOR.PATCH`. Пока `0.x`: новая возможность или заметное изменение
поведения — `MINOR`, исправление — `PATCH`. Релиз — это тег `vX.Y.Z` на коммите в `main`;
остальное делает `.github/workflows/image.yml`.

1. Отдельным PR «Релиз X.Y.Z»:
   - `npm version X.Y.Z --no-git-tag-version` — меняет `package.json` и `package-lock.json`;
   - в `CHANGELOG.md` раздел `[Unreleased]` становится `[X.Y.Z] - ГГГГ-ММ-ДД`, сверху
     остаётся пустой `[Unreleased]`. Всё, что написано под заголовком версии до первого
     `###`, станет текстом релиза на GitHub. Пиши там коротко и для тех, кто обновляется:
     что нового, что проверить и — отдельной строкой — что нужно сделать руками (если нужно).
2. После слияния — тег на `main`: `git tag vX.Y.Z && git push origin vX.Y.Z`.
3. Дальше автоматически: тесты, сборка образа для amd64 и arm64 с проверкой, публикация в
   `ghcr.io/gopro3400/max-in-tg` (теги `X.Y.Z`, `X.Y` и `latest`) и — отдельным заданием
   `release` — страница релиза. Тег, у которого версия не совпадает с `package.json`, который
   стоит не на `main` или для которого в `CHANGELOG.md` нет раздела с описанием, workflow
   отклонит до сборки (`scripts/release-notes.sh`).
4. После самого первого выпуска: GitHub создаёт пакет приватным, и задание `release` упадёт
   с понятным сообщением — страница релиза не появляется, пока образ нельзя скачать без
   входа (иначе бот пошлёт пользователей обновляться на образ, которого они не видят). Один
   раз сделай пакет публичным: профиль → Packages → `max-in-tg` → Package settings → Change
   visibility → Public — и запусти упавшее задание заново (Actions → запуск → «Re-run failed
   jobs»): повторится только оно, сборка не нужна.

Пользователи узнают о новой версии из бота (`UPDATE_CHECK`, раз в сутки) и обновляются одной
строкой `docker compose pull && docker compose up -d --no-build` — см. `docs/SETUP_GUIDE.md`
§13. Если изменение требует от пользователя ручных действий при обновлении, напиши об этом в
разделе `[Unreleased]` отдельной строкой «Что нужно сделать».

Откат на прежнюю версию работает, пока схема базы менялась только добавлением столбцов и
таблиц. Если изменение схемы этого не позволяет (что-то удаляется, переименовывается,
получает новое ограничение), скажи об этом в начале описания релиза: там же пользователю надо
будет вернуть и базу из `data/backups/`.

Форк, который публикует свои образы: замени имя образа в `image:` обоих compose-файлов
(CI это проверяет) и включи `UPDATE_CHECK_REPO` для своего репозитория.

## Приоритеты Ревью

Проверять изменения в порядке критичности:

| # | Приоритет | Описание |
|---|-----------|----------|
| 1 | **Безопасность** | Риск отправить сообщение не тому человеку |
| 2 | **Надёжность** | Потеря или дублирование сообщений |
| 3 | **Хрупкость** | Max Web селекторы могут сломаться |
| 4 | **Секреты** | Telegram-права и хранение credentials |
| 5 | **Деплой** | Docker/VPS deployability |
| 6 | **Edge cases** | Конвертация медиа, таймауты |

> Если изменение может привести к отправке сообщения в неправильный Max-чат → **fail closed**: не отправлять и сообщить об ошибке.

## Локальная Проверка

Нужен **Node.js 22** — на нём собирается образ (`node:22-bookworm-slim`) и работает CI (Node 20 с апреля 2026 не поддерживается).
На Node 18 нативная сборка `better-sqlite3` может упасть, и это будет выглядеть как
поломка проекта.

### Минимум (синтаксис)

```bash
node --check src/index.js
find src -name "*.js" -print -exec node --check {} \;
```

### Тесты

```bash
npm ci        # ровно то, что зафиксировано в package-lock.json — как в CI и в Docker
npx vitest run
```

### Полная сборка

```bash
docker compose -f docker-compose.prod.yml build
```

> Не запускайте production stack с реальными credentials, если `.env` не настроен под нужный аккаунт.

## Важные Соглашения

**Документация**

- Русская документация — основная. `README.md` — краткая русская версия и главная
  страница репозитория, `README.ru.md` — полная русская, `README.en.md` — английская.
  Изменение, затрагивающее UX или переменные, правится во всех трёх
- Пошаговая инструкция для новичков живёт в `docs/SETUP_GUIDE.md`, разбор медиа и
  селекторов — в `docs/MEDIA_PIPELINE.md`

**Безопасность и приватность**

- Источник правды по селекторам — **живой MAX Web**. Прежде чем добавлять или менять
  селектор, посмотри реальный DOM залогиненного клиента, а после изменения прогони
  `/check`
- Если есть риск отправки не тому человеку — блокировать отправку (fail closed).
  То же для тем: не удалось создать тему — сообщение не уходит в общий чат
- QR входа в MAX — это учётные данные: кто отсканирует, тот привяжет своё устройство к
  аккаунту. Только в личный чат владельца, никогда в группу
- Не логировать текст сообщений и содержимое QR: через мост идёт реальная переписка
  живых людей. Дампы диагностики редактируются (`sanitizeDiagnosticHtml`) — не добавляй
  путей, которые обходят редакцию
- `maxLock` **не реентрантен**: вложенный `maxLock.run()` внутри уже захваченного замка
  вешает мост навсегда
- Не ломать Telegram Topics модель ради удобства
- Селекторы могут измениться — делать их конфигурируемыми через `.env` и добавлять
  новые ключи в `.env.example`
